# 账单整理总体方法论 · 格式漂移应对手册

> 适用：recon_workbench 全部 11 个已接入平台。
> 读者：AI（主脑）与维护者。目标：**上游账单格式变更、新增字段、新增费用类型时，
> 能按本文引导人类对齐输出，而不是静默算错**。
> 平台细节见同目录 platform-*.md（每平台一份）。

## 0. 输入与输出约定（2026-11-16 用户需求）

**输入：用户可直接给平台原始下载的 zip 压缩包**（全平台一致）：
- file_paths / extra_files 给 zip 文件 → 自动解压到 `runtime/extracted/{zip名}_{哈希}/`
  （按 zip 路径+mtime 缓存，重复跑不重复解压）再收集；
- 给目录 → 递归收集子目录；**纯 zip 目录**（无任何已解压文件/子目录）自动解压；
  已有解压副本时不再碰 zip（防双份重复计账）；
- zip 内文件名 gb18030 编码兜底；防 zip-slip。

**解析失败时的沟通认知（重要）**：解压后找不到账单文件、或列头与平台预期不符时，
**第一假设是用户下载错了**（错平台/错账期/错报表类型），不是先怀疑平台改版。
错误 detail 已带 hint；AI 应把「解压出了什么文件/列头」摆给用户，
问「这是不是 X 平台 X 月的账单？是否下载错了？」确认后再考虑格式漂移修复。

**输出目录命名**（结果根目录由设置页自定义）：
- 普通平台：`YYYY-MM-中文平台名-店铺名称-店铺编号`（店铺名称用氚云名称），
  **重复运行直接覆盖**（清空旧批次目录重建），无时间戳/数字后缀；
- 爱库存：`YYYY-MM-爱库存`（一渠道多店 AKC003/AKC004，不写店铺段）；
- 唯品会：两层——第一层 `YYYY-MM-唯品会-唯品中国`（供应商默认唯品中国），
  第二层为旬交付文件 `唯品会_2026年0801-2026年0810唯品中国_账单整理.xlsx` 等，
  一个账期多旬在目录内**累积**（不清目录）；底稿按旬子目录隔离。
  给父目录/整批旬 zip 时 pipeline 自动识别旬结构逐旬跑（_vip_expand_xuns）。
- 交付 Excel 在批次根目录；manifest/表格/统一明细等过程产物在 `底稿/`。

## 1. 统一流水线（所有平台同构）

```
原始账单文件（csv/xlsx，平台各自编码与表头）
  → read()      按平台读取参数读入（encoding / skiprows / dtype）
  → clean()     平台特有清洗（去汇总尾行、剥 ="..." 与引号前缀、列缺失校验）
  → 分类        业务编码字典 → 备注关键字链 → 后处理细分（平台各异，顺序敏感）
  → normalize() 归一为标准五元：订单编号 / 资金日期 / 业务类别 / 收款 / 退款
  → 账期过滤    按资金日期 ∈ [s_date, e_date]（京东例外，见平台文档）
  → 落盘        批次目录：交付 Excel（影刀基准格式）+ 底稿/（统一明细/表格/manifest）
```

**两条出口，一个口径源**：
- **账单层**（全部业务类别）→ 透视 + 氚云导入模板 + 平台明细 sheet —— 财务交付；
- **匹配层**（货款行）→ bill_goods 底稿 —— 将来 SKU 对账输入。
  单源平台匹配层 = 账单层筛「货款」；**京东刻意不同**（见 platform-jd §6），不要"统一"。

**金额纪律**：内部一律整数「分」（int64），导出 Excel 转「元」两位小数。
自检对平必须**分位相等**，不许四舍五入抹平差异。

## 2. 分类的三层结构（漂移最常发生的地方）

| 层 | 机制 | 漂移表现 | 应对入口 |
|---|---|---|---|
| ① 编码字典 | 业务编码/费用项 → 业务类别（如 0010001→货款） | 平台新增费用编码 → 落「未匹配」 | **规则表 biz_code**（热修，无需改码） |
| ② 备注关键字链 | 编码未命中时按备注子串顺序匹配 | 平台改备注话术 → 落「其他」或错类 | 代码内 NOTE_RULES（**顺序敏感**，改码需回归） |
| ③ 后处理细分 | 特定类别按备注前缀再拆（保证金/支付服务费等） | 备注格式变（分隔符没了）→ 细分失效 | 代码内 *_split 函数（改码需回归） |

**关键原则：字典可热修，链序不可乱动。**
历史上两次重大回归差异都是「把链上某个关键字挪了位置」造成的精确镜像错分类
（淘系「软件服务费」提前 → 品牌新享 -839590 分镜像；京东 bustype_split 挪序 →
商家结算款对平判定翻转）。**任何链序调整必须跑基准回归后才可交付。**

## 3. 规则表（热修通道，AI 可直接维护）

文件：`{plugin}/rules/{platform}.json`，工具 `upsert_rule / delete_rule / query_rules`。
rule_kind 五类：

| kind | 用途 | 示例 |
|---|---|---|
| `biz_code` | 编码→类别映射（**整表覆盖**内置字典，见下方警告） | pdd: 0010002→货款 |
| `column_map` | 标准字段→平台原始列名（GenericAdapter 用） | order_no→业务基础订单号 |
| `read_option` | 读取参数覆盖 encoding/skiprows/drop_tail | skiprows=4 |
| `amount_sign` | 金额方向约定 | receipt_positive |
| `filter` | 行过滤条件 | （预留） |

⚠️ **biz_code 覆盖语义**：适配器 `biz_code_map()` 返回非空规则表时**整体替代**内置
兜底字典（不是合并）。

**2026-11-16 内置规则已剥离**：10 个平台的内置字典/读取参数已由
`scripts/seed_builtin_rules.py` 全量种子到 `rules/{platform}.json`
（note=builtin-default，259 条），管理页「平台解析规则」直接可见可编辑。
因此**日常热修只需 upsert 单条**，不再需要「首次先全量导入」。注意：
- 代码字典保留为兜底：规则文件被删或条目停用（active=0）时回落内置口径；
  **停用单条≠回落单条**——biz_code 只要还有任一启用条目就整表接管，
  想排除某编码应把其 value 改为「未匹配」而不是停用（停用会让它落字典外）。
- 副字典走 biz_code 命名空间前缀（不进主映射）：淘系微信 `wx_id:` / `wx_type:`、
  唯品会品牌 `brand:`、爱库存店铺 `shop:`（值=名称|编码|品牌）。
- read_option 值支持 JSON（dtype 字典等）；`drop_tail` 是清洗参数不是 pandas
  读取参数（base 已过滤，taobao 实证过 TypeError 坑）。
- 种子脚本幂等：重跑只补缺失键，**不覆盖**用户/AI 已改的条目。
- 备注关键字链（NOTE_RULES 等）顺序即口径，**仍在代码**，改序必回归。

## 4. 格式漂移分诊 SOP（发现异常先走这里）

### 第 0 步：症状分类

| 症状 | 大概率原因 | 跳转 |
|---|---|---|
| BillParseError「缺少字段 X」 | 上游改列名 / 改表头行数 | §4.1 |
| 读入 0 行 / 行数异常少 | 编码变了 / skiprows 不对 / 汇总尾行误删数据 | §4.1 |
| 透视出现「未匹配」「其他」「未知」类 | 新费用编码 / 新备注话术 | §4.2 |
| 金额对平门报错（E卡不平 / 支付宝收支不平 / 抖音金额差异≠0） | 新组件列 / 口径变化 | §4.3 |
| 类别金额与上月/影刀基准「精确镜像」 | 链序被改动 / 备注话术微调命中了别的关键字 | §4.4 |
| 京东商家结算款没被替换（透视只有钱包类） | 账期推断变了 / 结算单文件缺失 | platform-jd §4 |

### 4.1 列名 / 表头 / 编码漂移
1. `preview_bill(platform, file_paths)` 试跑（不落盘）→ 看 raw_columns 与报错 detail 里的 available_columns；
2. 用 pandas 直接探原始文件前 8 行确认新表头结构（encoding 逐个试 gb18030/gbk/utf-8-sig）；
3. **只改读取参数**（skiprows/encoding/drop_tail）→ `upsert_rule(read_option)` 热修；
4. **改了列名** → 需要改适配器 REQUIRED_COLUMNS / clean()（代码级），
   改前把新旧列名对照表给人类确认，改后跑 §5 回归；
5. 新增列但旧列都在 → 多数平台可容忍（抖音有 OPTIONAL_* 补 0 机制），
   但**新列若带金额**必须判断是否参与组件公式（§4.3）。

### 4.2 新费用类型 / 新编码
1. `query_bill_rows(batch_id)` 或读底稿统一明细，筛 业务类别 ∈ {未匹配, 其他, 未知}；
2. 汇总这些行的 原始编码/费用项/备注 + 金额合计，列成表给人类；
3. **引导人类定类**：每个新编码/话术属于哪个业务类别？是否货款（影响 SKU 对账）？
   给人类的选项应含：归入既有类别 / 新建类别（会出现在透视与氚云模板）/ 挂「未匹配」待下期定；
4. 编码类 → 走 §3 biz_code 热修；备注话术类 → 改 NOTE_RULES（放对位置！新关键字
   若与既有关键字有包含关系，必须排在更特异的在前），改后跑 §5 回归；
5. 处理完重跑该店该账期，确认「未匹配/其他」金额清零或仅剩人类确认挂账的部分。

### 4.3 金额自检门不平
三个平台有硬门（不平即 BillParseError，绝不静默）：
- 京东：钱包 E卡货款现金流 == E卡表合计（分位）；
- 淘系支付宝：透视收/退合计 == 原始收/支合计（分位）；
- 抖音：明细「金额差异」列 = 动账金额 - 各组件之和，应恒 0。
不平的处理：**先找钱去了哪**，把差额行定位出来（通常是被漏算的新组件列或
被错误归类的行），列差额明细给人类，确认口径后再改公式。禁止调容差放行。

### 4.4 精确镜像差异
两类金额一正一负恰好相等 → 几乎必是分类链顺序问题。diff 出两类的行集，
对照 NOTE_RULES 链序与备注原文，恢复/修正顺序，回归验证。

## 5. 变更后的验收（不可跳过）

1. **基准回归**：用 `E:\AIcoding_project\xbot_robot\历史运行结果` 的 8 月真实账单 +
   影刀基准 Excel 逐 sheet 比对（列头含重名列 / 行数 / **全部数值列合计**，
   参考工作区 scripts/verify_export_baseline.py 的比对方法）。
   ⚠️ 教训：只比金额列会漏掉毛利率等结构性缺陷（假绿）——比对列必须全覆盖。
2. **新账单试跑**：`preview_bill` 新月账单 → 确认列名/行数/未匹配占比；
3. **正式跑 + 自检门**：start_recon 后看终态与 notes；
4. **人类对齐**：把「新增类别清单 + 金额 + 归类依据」发给人类确认后才算对齐完成。
   输出对不上的行，宁可挂「未匹配」暴露，不许悄悄归进「其他」。

## 6. 每月新账期的例行检查单（AI 主动执行）

- [ ] 各平台文件齐全？（京东三源、淘系微信子目录、抖音/拼多多 csv）
- [ ] preview_bill 无缺列报错、行数与上月同量级？
- [ ] 「未匹配/其他/未知」金额占比 < 上月？异常增长即触发 §4.2；
- [ ] 三个金额自检门全过？
- [ ] 京东 inferred_period 与账单月吻合（跨月边界正常，见 platform-jd）？
- [ ] 透视类别数与上月 diff：新增类别 → §4.2 引导人类定类；消失类别 → 确认是业务消失还是漏判；
- [ ] 交付 Excel 与氚云导入模板类别一致。

## 7. 交付物结构（对齐输出的锚点）

批次目录根 = 财务交付件（与影刀同名同 sheet 结构）：
- 抖音/拼多多：`{平台}_{店铺}_{编码}_{账期}_账单整理.xlsx`（模板+透视+明细）
- 淘系：支付宝汇总结果 + 账单分类明细 + 微信账单整理（三簿）
- 京东：京东钱包整理 + 京东账单整理（两簿；E卡簿在底稿/）
`底稿/` = manifest.json、统一明细.xlsx、bill_detail/goods 表格、京东E卡簿。
**店铺名称一律用店铺映射的「氚云名称」**；映射缺失会回落 shop_code 并带 note——
见到该 note 先引导人类提供 OMS店铺.xlsx，再继续。
