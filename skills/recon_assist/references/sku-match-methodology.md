## 0. 业务本质与会计语境

平台账单里的每一笔**货款**（收款/退款），都要找到对应的**货物单据**（发货/退货入库），
才能决定财务上怎么记账。钱和货互相追认，就是「追账」。

会计背景（判断标签的语义基础）：
- 发货时：借「发出商品」、贷「库存商品」——货出去了但收入未确认，成本挂在**发出商品**科目；
- 收款核对成功 → **结转成本**：借「主营业务成本」、贷「发出商品」；
- 退货入库，对应发货**从未结转成本** → **冲发出商品**：借「库存商品」、贷「发出商品」；
- 退货入库，对应发货**以前期间已结转成本**（或找不到出库）→ **冲成本**：借「库存商品」、贷「主营业务成本」；
- **成本不做处理**：不做成本分录（钱对不上货、秒退、分摊≤0、已对账重复收款等）。

五类财务判断 = 结转成本 / 冲成本 / 发出商品（挂账状态，不是分录用词）/ 冲发出商品 / 成本不做处理。
代码中「处理意见」只有四种标签；「发出商品」是出库单未参与收款核对时的**挂账状态**：
货已发、钱未到，成本留在发出商品科目等下月收款，本月不出分录。

## 1. 取数逻辑（oms_sql_select，L168）

### 1.1 为什么向前取 X 个月（默认 6，用户确认）

**平台结算滞后**：本月账单收到的货款，对应的发货可能发生在几个月前
（确认收货周期、平台结算周期、账期拖延）。若只取本月 OMS，大量收款会误判「未匹配」。
因此取数窗口 = **账期开始日往前推 X 个月（默认 6） ~ 账期结束日 + 1 天**：

```
start = s_date - X 个月（relativedelta）
end   = e_date + 1 天
SELECT … FROM mid_jedz_datas
WHERE bill_date >= start AND bill_date < end AND shop_code = 店铺编号
```

- X 原为影刀弹窗人工输入（month_no）；插件定为 settings `oms_lookback_months` 默认 **6**，可按批次覆盖；
- 右边界 +1 天：覆盖账期最后一天全天（bill_date 含时间分量）；
- 单店 6 个月窗口数据量很大（PDD002 实测约 41.6 万行）→ **只在内存匹配，不整表落地**；
- 窗口大 ≠ 重复对账：靠 §5 的历史对账状态闸门防重。

### 1.2 三类单据拆分（bill_type 只有三种取值）

| 字典键 | bill_type | 方向 | 预处理 |
|---|---|---|---|
| OMS出库 | B2C配货单 | 发货 | id 转 str |
| OMS入库 | B2C退换货通知单 | 退货入库 | id 转 str |
| OMS退款 | 退款单 | 平台退款记录 | 按 **单号+sku+结算金额** 拼接去重（L240） |

关键字段（真实英文列名见 SKILL.md「巨益 ADB 真实表结构」）：
- `id`：明细主键，**回传的唯一依据**；
- `bill_state` → 历史对账记录：`未对账` / `已对账`；
- `bill_period` → 对账周期：上次对账写入的中文账期标签（`2026年06月-2026年06月`）；
- `settlement_amount` → 结算金额：Decimal **元**，订单口径金额，分摊权重；
- 三类全空 → 终止（插件语义 status=skipped，新店首月/本期无发货属正常）。

### 1.3 辅助数据源（同一 ADB 连接）

- `AI_product_info`：按 sku 批量查（每批 4000，L1249）补 款号/商品名称/品类/年份/季节/品牌/吊牌价/标准成本单价；
  标准成本 = 数量 × 标准成本单价；品牌字典归一（COCOON→CO、秋水伊人→QS、FirstView→FV…）；
- `je_saleorders`：订单日期缺失且非秒退的行，按 trade_no 批量查补（L1409）。
  注意 trade_no 不唯一，插件已改 ORDER BY 取最新 order_date（有意改进，见 SKILL.md）。

### 1.4 账单侧输入（bill_arrange，L303）

各平台列名映射为统一五元后：只留 **业务类别=货款**；货款金额 = round(收款,2) - round(退款,2)；
收款、退款**分别**按订单号 sum 透视（一单一行）；空订单号填「无订单号」；金额 0 行剔除。
京东特殊：结算单+钱包+E卡三源（钱包「货款退款」从备注正则提取订单号）；
匹配窗口用钱包备注资金日期 min~max（`artifacts.match_window()`），不等于账单账期。

## 2. 收款段对账（L650）

1. **主匹配**：账单收款 left join OMS出库 on 订单编号（以账单为基准）。
   一对多展开时 `duplicated('订单编号')` 的重复行**货款金额置 0**（金额只记首行，防重复计金额）；
   有单号 → 已匹配；无 → 未匹配。
2. **秒退交叉核对**（L755，收款侧发起）：
   - 取未匹配收款订单号列表，到退款整理结果中汇总同订单货款金额
     （筛选条件含 单据类型为空/退款单 的行，L767）；
   - `round(收款货款,2) == round(退款合计,2)` → **是否秒退判断=是**（钱收了又全退，货可能根本没发）；
   - 已匹配行强制清空秒退标记（L794）；
   - 秒退的收款行**单独再撞一次 OMS退款单**（L818），拿回 sku/单号信息，避免误判「无发货」；
   - 非秒退部分与再匹配部分 concat 回收款表。
3. **收款侧被并入的出库**（来自 §4 额外入库判断）：标「已匹配 + 成本不做处理」，
   货款金额/分摊为 NaN——这些是「货发了又整单退回、从未确认收入」的出库单。

## 3. 退款段对账（L685）

1. **两段匹配**：
   - 第一段：账单退款 left join **OMS入库**（B2C退换货通知单）on 订单编号；重复行货款置 0；
   - 第二段：仍未匹配的（只带 订单编号/货款金额/账单周期 三列）再 left join **OMS退款单**；
     重新判已匹配/未匹配后与第一段已匹配部分 concat。
   - 为什么两段：入库单证明**货回来了**（成本判断依据）；退款单只证明**钱退了**（平台侧记录），
     有入库优先用入库，退款单兜底补 sku 信息。
2. **秒退反向标记**（L860）：收款侧秒退=是 的行分两路回标退款表：
   - 单据类型=退款单 的 → 按**单号**集合标记退款表同单号行；
   - 单据类型为空的 → 按**订单编号**集合标记退款表同订单行。
3. **额外入库判断**（L890，冲成本/冲发出商品的来源，见 §4）。
4. 退款侧同样跑分摊（§6）与处理意见判定（§5）。

## 4. 额外入库判断（L890–1193）— 没有退款账单的退货怎么记

场景：货退回来了（有入库单），但本期账单**没有对应退款**（平台还没退钱/上期已退）。
这部分入库单不能漏记成本，逻辑（源码注释十步，L892）：

1. 取 OMS入库，过滤：**存货异动日期在账期内** & **历史对账记录 ≠ 已对账**（L958）；
2. 剔除已被退款核对占用的单号（res_pay 中 B2C退换货通知单 的单号列表，L967）；
3. 剩余入库单构造 `订单编号_sku` 与 `订单编号` 两个键列表；
4. 到 OMS出库 找对应发货，条件（L978）：
   - 订单_sku 命中入库键列表；
   - **未参与收款核对**（订单_sku 不在收款已匹配列表）；
   - **历史未对账**；
5. 找到的出库（df_out_sku）→ 并入**收款表**，标「已匹配 + **成本不做处理**」
   （货发了又退、从未确认收入 → 不结转，成本留在发出商品等冲回）；
6. 入库单打标（L1017）：
   - 订单_sku 命中上述出库 → **冲发出商品**；
   - 订单_sku 未命中、但**订单号**命中同订单其它未核对出库（df_out_nosku，换码/拆单场景）→ 也标 **冲发出商品**；
   - 两者都未命中 → **冲成本**（对应发货在更早期间已结转成本，或窗口内找不到出库）；
7. 找不到任何对应出库（df_out_sku 为空）→ 全部入库标 **冲成本**（L1058/1077/1189）；
8. 全部入库标「已匹配」，concat 进**退款表**。

> 直觉记忆：**冲发出商品 = 本期发货本期退（收入从未确认）；冲成本 = 退的是以前结转过的货**。
> 区分依据不是时间，而是「对应出库是否参与过收款核对/是否已对账」。

## 5. 处理意见判定与状态闭环（L1429–1557）

### 5.1 C 列：账期先后比较（L1430）

`C = compare(账单周期, 对账周期)`：对账周期为空 → 0；账单周期为空 → 1；
否则解析中文标签为 YYYYMM 整数，账单周期 > 对账周期 → 1，否则 0。
**C=0 才允许给新的成本分录**；C=1 表示「这笔单据在更早账期已对过账」→ 拦截。

### 5.2 收款侧三段判定（顺序执行，后者覆盖前者）

| 段 | 条件 | 结果 |
|---|---|---|
| 第一段 L1462 | 处理意见为空 & B2C配货单 & 非秒退 & **C=0** & **历史≠已对账** | 结转成本 |
| 兜底 L1473 | 其余空意见 | 成本不做处理 |
| 第二段 L1476 | 分摊>0 & 数量>0 & 非秒退 & C=0 | 补判 结转成本（分摊对上即认） |
| 第三段 L1486 | 账单周期为空 \| 分摊≤0 \| 秒退=是 | 强制 成本不做处理 |
| 状态回退 L1496 | 分摊≤0 & 历史未对账 & 账单周期非空 | 匹配状态改回 **未匹配** |

### 5.3 退款侧判定 + 交叉修正

- 第一段 L1507：空意见 & B2C退换货通知单 & 非秒退 & C=0 & 历史≠已对账 → **冲成本**；其余空 → 成本不做处理；
- **交叉修正一** L1524：收款侧「成本不做处理」的 订单_sku → 退款侧同键的 冲成本 改 **冲发出商品**
  （收款侧已认定这笔货从未确认收入，退货应冲发出而非冲成本）；
- **交叉修正二** L1534：收款侧「结转成本」的 订单_sku → 退款侧同键的 冲发出商品 改回 **冲成本**
  （收款侧已结转，退货必须冲成本）。
- 注意 L1536 源码用 `if not df_out_.empty`（应为 df_out__）——疑似笔误，迁移时按意图修正并登记。

### 5.4 状态闭环（每月循环的核心）

```
本月对账完成 → 回传表（历史未对账 & 已匹配 的行按 id 透视 [id,账单周期,数量]，L1543）
→ update_sql：UPDATE mid_jedz_datas SET bill_state='已对账', bill_period=中文账期 WHERE id=…
   （每批 1000 提交，失败回滚；成功文件移入 执行成功/，失败留守）
→ 下月取数（窗口仍覆盖这些旧单据）时：
   · 历史对账记录=已对账 → 第一段判定拦截；
   · 账单周期 > 对账周期 → C=1 → 第一/二段都拦截；
   · 同一订单号的新收款（滞后结算尾款）→ 意见落「成本不做处理」，不重复结转；
   · 已对账单据不进回传表（L1546 过滤历史未对账）→ 不会二次写状态。
```

**这就是用户口径「下个月对已对账的相同订单号收款部分，不做成本处理」的实现机制**：
窗口向前取 6 个月保证旧单据可见，状态闸门保证旧单据不重复记账。
账期标签必须用 `period_label()` 中文格式（`2026年06月-2026年06月`），
写 `YYYY-MM` 会让同一账期在生产库裂成两种写法，C 列解析也会失败。

## 6. 货款分摊（calculate_receipt_allocation，L56）— 收款/退款共用

按订单把货款金额分到 SKU 行，四级策略（依次尝试）：
1. 分摊基数 = 结算金额>0 的行；合计与货款相等（容差 1e-6）→ 按结算金额直分；
2. 某单行结算金额 == 货款 → 全给该行，其余 0；
3. **子集组合 DP**：SCALE=1e6 整数化，降序贪心+动态规划凑目标，精确命中或 |差|≤1（即 1e-6 元）；
4. 都不行 → 按结算金额比例 round(2) 分摊，**末行兜底补差**。

边界：未匹配 → 分摊=货款原值；货款 NaN → 0；结算金额全≤0 且合计≈0 → 首行拿全部货款。
最后 `groupby('订单编号').transform(duplicated→0)` 再次保证货款金额一单只记一行。

**硬门（L1202/1215）**：收款、退款各自 分摊合计 - 货款合计 ≡ 0（round 2），
不等 → 程序终止。插件口径：分为单位 int，差异恒 0 分；不许调容差放行。
插件迁移注意：分 int 下 DP 精确命中即可（无浮点误差），比例分摊末行补差保证恒 0。

## 7. 输出与透视口径

每店一份 6-sheet Excel：店铺数据透视 / 款号数据透视 / 匹配透视 / 收款匹配 / 退款匹配 / 已匹配的巨益单号。
- 明细 32 标准列 + 数据来源 + 店铺编码（core/matching.py DETAIL_OUTPUT_COLUMNS）；
- 透视只取特定意见：收款侧 **结转成本**；退款侧 **冲成本** 与 **冲发出商品** 分列
  （款号/店铺透视退款段处理意见显示「冲成本/冲发出商品」，标准成本=冲成本部分，冲发出商品=另一列）；
- 收款正数、退款负数；毛利=分摊金额-标准成本；毛利率 round(4)，分母 0→0（插件以 bp 存）；
- 全 0 行删除；**回归比对列必须含毛利率列**（假绿教训）；
- 已知源码笔误 L1804–1805：链式赋值把「冲发出商品数量」覆盖成标准成本金额——spec Q3 待确认修正。

## 8. 平台分流

- B2C 平台：走 §1–§7 全链；
- 京东：三源合并在账单整理层完成，match 层只消费 bill_goods + match_window。

### 8.0 渠道分流实证（main.py 调用链，勿凭直觉归类）

| 渠道 | 账单整理 | SKU 对账路径 | OMS |
|---|---|---|---|
| 淘系/支付宝/微信/抖音/PDD/视频号/快手/有赞/得物/小红书/京东 | 各适配器 | **B2C 主链 result()** | 查 |
| **好衣库 HYK**（L559-601） | hyk_arr | **B2C 主链**（hyk_arr→bill_arrange→oms_sql_select→result） | **查** |
| **爱库存 AKC**（L602-629） | akc_arr | **B2B_match**（cus_select=爱库存） | 不查 |
| **唯品会 VIP**（L630+） | wph_arr 逐旬 | **B2B_match**（弹窗选 唯品中国/唯品重庆） | 不查 |

⚠️ 好衣库虽是"卖给平台"渠道，但原系统按 B2C 处理（查 OMS、全匹配链、参与状态回传）——
不要凭业务直觉把它归入 B2B。

### 8.1 B2B 分流（爱库存/唯品会，B2B_match L2031）

B2B 是「货卖给平台」的结算口径，不存在钱找发货单的问题，**整条 B2C 匹配链不适用**：

| 维度 | B2C 主链 | B2B（B2B_match） |
|---|---|---|
| OMS 取数 | 向前 6 个月三类单据 | **不查**（账单自带 sku/数量/结算金额） |
| 匹配/分摊 | 订单匹配 + 四级分摊 + 对平门 | 无（直接按账单行算成本） |
| 秒退/额外入库 | 有 | 无 |
| 处理意见 | 五类判定 + 交叉修正 | 收款→结转成本；退款→冲成本（L2085/2121） |
| 回传 | 已匹配巨益单号 id 表 | **空表，不参与状态闭环** |

### 8.2 唯品会特例（差异最大平台，账单层详见 platform-vip.md）

1. **按旬出账**：一个账单月=三旬（上月下旬+本月上中旬），三旬交付文件同目录累积；
   SKU 对账按旬文件逐份处理，不做行级日期过滤；
2. **账期标签带日**（check_dates L47）：`2026年0801-2026年0810`（年+月日），
   区别于其它平台 `2026年08月-2026年08月`——按旬结算必须精确到日；
   C 列账期解析/回传标签逻辑对唯品会不适用（无回传）；
3. **多店一簿**：品牌反推店铺（SHOP_BY_BRAND），透视按店铺分组；
   品牌=名称字典映射后按款号前缀规则覆盖（顺序敏感：8+字母→FR / 42+数字→MyALL /
   7开头→MyAll(菁禾) / 3开头→YUUSAAY / 5+数字→C3）；
4. **FR 品牌成本特例**（L2217–2229）：FR 标准成本 = **结算金额**（收款、退款两侧都覆盖，
   不用 数量×标准成本单价）——FR 代销/联营性质，成本即结算额、毛利为 0；
   成本匹配阶段 FR 发货成本=标准成本（cost_match.py 同口径）；
5. 全部行业务类别=货款，无费用分类链；金额舍入顺序特例（先含税 round(2) 再除税；H 表税率不 round）。
