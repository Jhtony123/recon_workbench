# 淘系（taobao：淘宝 + 天猫）账单整理 · 平台技能文档

> 适配器：`core/platforms/taobao.py`（承接 bill_arr.zfb_complex_arr ≈558 行 +
> wechatpay_arr ≈380 行）。淘宝店与天猫店共用同一适配器（platform=taobao），
> 区别只在店铺编码/名称与账单内容；天猫特有类别（天猫佣金/天猫保证金等）由编码字典自然覆盖。
> 总体方法论见 bill-methodology.md。

## 1. 数据源：双源（支付宝主源 + 微信附加源）

| 源 | 位置约定 | 读取参数 | 必需列 |
|---|---|---|---|
| **支付宝账务明细** | file_paths 目录下 `*.csv`（文件名形如 `2088…0156_202608_账务明细.csv`） | `gb18030, skiprows=4`，读后**无条件去尾 4 行**汇总（read_option/drop_tail 可调） | 商户订单号/发生时间/对方账号/商品名称/收入金额（+元）/支出金额（-元）/业务类型/备注/业务基础订单号/业务描述 |
| **微信支付账单** | `extra_files={"wechat":["<root>/微信"]}`，**.xlsx** | read_excel，ID 列 dtype=str | 入帐时间/主订单id/支付流水号/入帐类型/备注/收入金额(元)/支出金额(元)/业务描述 |

- 微信源可缺省（只出支付宝两簿）；**用户没提微信时 AI 应主动问/检查店铺目录下有无「微信」子目录**——
  漏了微信源不报错，但账单缺一块（历史坑：collect_files 只收 .csv 漏掉微信 xlsx，已修）。
- **两渠道必须一起跑，不能分开**（2026-11-16 用户口径）：同一订单号可能混合支付
  （既有微信结算又有支付宝结算），分开跑会把同一订单的资金拆到两个不完整批次里，
  后续 SKU 交叉对账对不上。淘宝/天猫主体是支付宝月账单，微信收费渠道账单不一定有；
  有则 extra_files.wechat 一并给（支持 zip）。
- 微信字段带反引号 \` 前缀（Excel 文本保护），清洗时剥掉；注意「入**帐**」不是「入账」。
- 金额列名全角括号（支付宝）vs 半角括号（微信），上游改括号宽度=缺列报错。

## 2. 两条完全独立的分类链（本平台最大红线）

**支付宝链与微信链不是同一条链**，2026-11-14 曾合并导致 5 家店精确镜像差异。差异点：

| 维度 | 支付宝链 | 微信链 |
|---|---|---|
| 编码字典 | ALIPAY_ID_DICT（**含货款类** 0010001-4/0020001-2/0160001/0640003 等） | WECHAT_ID_DICT（**不含货款类**，货款靠入帐类型兜） |
| 货款来源 | 编码字典 | 入帐类型 WECHAT_TYPE_DICT：交易收款/交易退款(售后)→货款 |
| 备注链触发条件 | **业务编号为空**（""/nan/无分类/None） | **类别为空**（字典+入帐类型都没命中） |
| 备注链内容 | 有「太保财险→财产保险」「天猫保证金履约险_退保保险费→天猫保证金」；「投诉理赔」须同时含「客户服务中心投诉处理组」 | 有「淘宝新客礼金技术服务费」「消费券价格管控补贴」「万相台无界版聚合充值」「保证金管控资金使用→货款」等专有词；「投诉理赔」无附加条件 |
| 后处理 | deposit_split + **pay_service_split**（支付服务费取备注`[`前缀）+ **hotwave_split**（热浪引擎取`(`前缀）+ type_from_other（其他→企业红包/提现/结息/第三方转账/充值）+ T62-改判货款 + **fright_type**（运费险取`-`与`收`之间） | 仅 deposit_split |

**顺序红线**：两条链里「品牌新享」都在「软件服务费」三分支**之前**。
曾把软件服务费提到链首 → TM001 品牌新享 -839590 分 / 软件服务费 +839590 分精确镜像。
新增备注关键字时：与既有词有包含关系的，更特异的排前面；改序必须跑基准回归。

## 3. 支付宝十步链（顺序即口径）

① 业务编号→id_dict ② 0020011+业务类型含「退票」→提现 ③ 货款+商品名称含「充值」→取「值」前缀
④ 业务编号为空→备注链 ⑤ deposit_split（天猫保证金按`-`前缀；含「保证金退款」→货款；
无`-`且备注<31字符→备注原文当类别！）⑥ pay_service_split ⑦ hotwave_split
⑧ type_from_other ⑨ 备注含 T62- 且有金额→货款 ⑩ fright_type。

⚠️ ⑤ 的「备注原文当类别」与 ⑥⑦⑩ 的「前缀当类别」意味着：**上游备注格式微调会直接
造出新类别名**（不是落未匹配）。每月透视类别 diff 是发现漂移的主通道。
原脚本 ⑥⑩ 在找不到分隔符时会崩（UnboundLocalError），插件保守返回原类别——这是
有意的健壮性改进，对齐影刀时若影刀侧崩了属预期差异。

## 4. 金额硬门

支付宝透视收款合计 == 原始收入合计、退款合计 == -原始支出合计（分位），
不平 → BillParseError（原脚本 exit()）。分类链无论怎么改，**钱不能丢**；
不平说明有行金额被吞（如类型转换失败 fillna(0)），先 diff 原始 vs 归一合计定位行。

## 5. 规则热修通道

- `biz_code`：覆盖支付宝 id_dict（**整表覆盖**语义，见方法论 §3 警告）。
  微信字典目前**不走规则表**（代码内 WECHAT_ID_DICT/TYPE_DICT），微信新编码需改码+回归。
- `read_option`：encoding / skiprows / drop_tail（支付宝尾行汇总数变了改这里）。
- 新编码定类引导：把「未匹配/其他/未知」行的 业务编号+业务类型+备注+金额 列表给人类，
  确认归类后：支付宝→规则表热修或改 ALIPAY_ID_DICT；微信→改码。

## 6. 交付物（三簿）

- `淘系店铺_支付宝_{店名}_{编码}_{账期}_汇总结果.xlsx`：氚云导入模板 + 汇总结果（8 列透视）
- `淘系店铺_支付宝_…_账单分类明细.xlsx`：**每个业务类别一个 sheet**（全列；sheet 名 31 字符截断去重）
- `淘系店铺_微信支付_…_淘系微信账单整理.xlsx`：模板 + 微信支付账单透视 + 微信支付账单 7 列
  （淘宝订单编号/资金发生日期/业务类别/收款/退款/业务描述/备注）

订单编号口径：支付宝取「业务基础订单号」（不是商户订单号）；微信取「主订单id」。

## 7. 漂移应对速查

| 症状 | 先查 | 修法 |
|---|---|---|
| 「缺少字段」 | 全角/半角括号、列名改名、skiprows | read_option 热修或改 REQUIRED_COLUMNS |
| 行数比上月少一截 | 尾行汇总行数变化（drop_tail=4 误删数据） | read_option/drop_tail |
| 微信簿整个没出 | extra_files.wechat 没给 / 微信目录改名 / xlsx 改 csv | 补 extra_files；格式变了改 _read_wechat |
| 透视冒新类别 | 备注前缀细分类（§3⑤⑥⑦⑩）/ 新编码 | 引导人类定类；编码走 biz_code |
| 「其他」金额增大 | 备注话术变化未命中链 | 补 NOTE_RULES（放对位置+回归） |
| 两类别精确镜像 | 链序被动过 | 恢复顺序，回归（§2 红线） |
| 收支合计门不平 | 金额列格式变化（千分位/货币符号）fillna(0) 吞钱 | diff 原始 vs 归一，修金额清洗 |

基准回归锚点：TBQY001 2026-08（支付宝 23 类 + 微信 13 类逐分对平），
TM001/TM003/TM006/TB002 为链序敏感店，改链后必须全部重跑。
